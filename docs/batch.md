# Phase 2 batch design

Customers and products are stable dimensions; orders have multiple items, zero or one payment, and eligible shipped items can have returns. Inventory is a static snapshot. IDs are stable for each order range so retries and overlapping ranges do not duplicate rows. This is append-only incremental loading, not change data capture or updates to existing records. The Python validator checks keys, required values, relationships and monetary reconciliation. PostgreSQL enforces primary/foreign keys, uniqueness and basic checks. The loader uses bounded SQL INSERT chunks in one transaction through the Compose PostgreSQL service, with no third-party Python dependencies. Audit rows record submitted counts, timestamps and status; they do not measure inserted counts. A database outage can prevent failure recording. Integration tests use a disposable database. Future phases will replace this local source simulation with streaming and lakehouse ingestion.
